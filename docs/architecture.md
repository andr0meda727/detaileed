# Architecture

How the monorepo is organised, and the rules that keep it that way. ESLint enforces the import rules in both apps
(`featureSlices` in `packages/config/eslint.js`), so a violation fails `pnpm lint` and CI.

```
apps/dashboard/     studio management SPA (Vite, React, TanStack Router) on app.detaileed.com
apps/web/           customer site (Next.js App Router) on detaileed.com
packages/ui/        design system: theme tokens and generic components (@detaileed/ui)
packages/domain/    pure TypeScript shared by both apps: time zones, labels, money, API errors, listing model
packages/api-client/ fetch layer and React Query hooks generated from the backend's OpenAPI spec
packages/config/    shared TypeScript, ESLint and Prettier config
docs/               this file, the re-architecture plan, the manual regression checklist
```

Everything in code is English: folders, files, URLs, query parameters, identifiers, comments, tests. Polish appears
only in text people see.

## Layers (both apps)

Imports flow one way: `app → routes → features → shared`.

- `shared` has no business knowledge and never imports a feature, a route or `app`.
- A feature imports `shared`, and other features **only through their entry**: `index.ts` (and, in the customer
  site, `server.ts` for server-only code). Everything else in a feature folder is private to it.
- Routes and `app` import features through the same entries.
- Nothing calls `fetch` directly; requests go through `@detaileed/api-client` (generated functions and hooks, or
  `apiFetch` for endpoints not in the spec yet).

## A feature

```
features/<name>/
  api/          React Query hooks on top of the generated client (queries, mutations, invalidation)
  components/   screens and the components they are built from
  hooks/        UI hooks used by several components of the feature
  model/        types, pure functions (filters, formatting, normalisers), zod form schemas; unit tested
  index.ts      the public API: what other features, routes and app may use
  server.ts     (customer site only) the server-only public API, e.g. loading data for a page
```

When a feature's components serve more than one screen, they get one sub-folder per screen or sub-area
(`bookings/components/{form,tasks}`, `inventory/components/{items,ledger,settings}`,
`planning/components/{settings,board}`); parts used by several of them stay at the `components/` root. A feature
with one screen keeps its components flat.

## Dashboard (`apps/dashboard/src`)

```
main.tsx            entry: api client setup, renders app/App
app/                composition root: App (providers), router, auth guards, api setup, layout (Sidebar)
routes/             TanStack Router file routes; thin: guards, search params, which screen to render
  __root.tsx
  (auth)/           login, set-password, accept-invitation (URL /login, …; a group adds no path)
  _signed-in.tsx    pathless layout: redirects to /login without a session
  _signed-in/       studios, and s/$studioId/* (the screens inside a studio, with the sidebar layout)
features/           auth, studios, bookings, clients, services, inventory, team, settings, reports,
                    dashboard-home, marketplace, booking-requests, planning
shared/             assets/ (logo), hooks/, lib/ (supabase, paging, queryClient, studio roles, …), ui/
routeTree.gen.ts    generated by the router plugin; committed (CI fails if it is stale)
```

Route ids include groups and layouts (`'/_signed-in/s/$studioId/requests'`, `'/(auth)/login'`); links and redirects
use URLs (`to: '/login'`). `getRouteApi` in a feature takes the id.

Features: `auth` (sign-in, invitations, password, user settings), `studios`, `bookings`, `clients` (clients and
their vehicles), `services`, `inventory` (stock, categories and the ledger: movements, materials per service, size
factors, consumption per visit, forecast), `team`, `settings` (the studio settings screen, composed of tabs from
other features), `reports`, `dashboard-home`, `marketplace` (the studio's public profile on the customer map),
`booking-requests` (requests customers send from the map; pending count in the sidebar), `planning` (bays, opening
hours, rules, closures; the day board; free slots for the booking form).

## Customer site (`apps/web/src`)

```
app/                Next.js routes only (plus the root layout, providers, robots, sitemap, error pages)
  (public)/         the map (/) and a studio's page (/studio/[id]); indexed by search engines
  (auth)/           sign-in, sign-up, forgot/reset password, confirm email, /auth/callback;
                    layout = the narrow page column + noindex
  (customer)/       signed-in pages: /account/* and /studio/[id]/book; layout = noindex
features/           search, studio, booking, account, auth (each with index.ts; studio also server.ts)
shared/             lib/ (site settings, Supabase clients, server api setup, query client), ui/ (header, footer)
proxy.ts            refreshes the Supabase session cookie on every page request
```

- A new page goes into the group of its audience. A group's layout holds only what all its pages share.
- Guards stay in the page or layout that knows the return path (`signInPath('/account')`, the booking URL with its
  query); a group layout can't see the path.
- Server components call only public endpoints, through `shared/lib/api/server.ts` (cached 60 s like the API).
  Signed-in calls run in the browser through React Query, with the token from the Supabase browser client.
- Server-only modules start with `import 'server-only'` (`shared/lib/api/server.ts`, `shared/lib/supabase/server.ts`,
  `features/studio/api/server.ts`): importing one from a browser component fails the build, so the server's
  token-less api config can never replace the browser's.
- Studio pages are ISR (`revalidate = 60`).

## Data

- Server state lives in React Query only. Each feature's `api/` wraps the generated functions and owns the query
  keys it invalidates. Generated query keys start with the API path (`['/api/Bookings', …]`), so invalidating that
  prefix refreshes every list of that resource.
- Responses are normalised in the feature's `model/` (`toBooking`, `toInventoryItem`, `toListing`): the API may send
  decimals and ids as strings, and money is in złoty (`formatPln` in `@detaileed/domain/money`).
- Paged lists that a screen computes over (stats, calendars) load every page with
  `shared/lib/paging.ts#fetchAllPages`. Prefer server-side filtering and paging for new screens.
- Mutation errors are toasted globally (`shared/lib/queryClient.ts` in both apps); a mutation whose screen shows the
  error itself sets `meta: { skipGlobalError: true }`. Turn API errors into text with `getApiErrorMessage`.
- Dashboard: the current studio comes from the URL (`/s/$studioId`). The layout route checks it against the user's
  studios and makes it the active one (`features/studios/model/activeStudio.ts`), which the api client sends as
  `X-Studio-Id`. Components read it with `useStudio()`.

## UI

- URL state (filters worth sharing) goes in the route's `validateSearch` (dashboard) or the query string read in a
  client component (customer site, so ISR pages stay static).
- Derive values instead of syncing them with `useEffect` + `setState` (an ESLint error). To reset a form when a
  modal opens, remount it with a new `key`.
- Generic UI comes from `@detaileed/ui`. `shared/ui` in an app keeps only that app's own UI.
- Styling: Tailwind v4. Tokens, base styles and shared utilities live in `packages/ui/src/styles/theme.css`
  (imported as `@detaileed/ui/theme.css` after `tailwindcss`, with `@source` pointing at the package so its classes
  are generated). Use tokens, not hex.
- Keep components under about 250 lines.

## packages/ui

```
src/
  index.ts      the package entry (components, toasts, captcha)
  components/   Badge, Button, EmptyState, FormInput, FormSection, LoadingSpinner, Modal, Select, Skeleton, StarRating
  toast/        ToastProvider, useToast and the toast list
  captcha/      Turnstile widget and useTurnstile
  hooks/        useIsClient
  map/          MapView, MapPicker (MapLibre), geo helpers; separate entries @detaileed/ui/map and /map/geo,
                loaded lazily by the apps so MapLibre stays out of the main bundle
  styles/       theme.css (@detaileed/ui/theme.css)
```

A new generic component goes in `components/` (or a folder of its own when it comes with hooks or context, like
`toast/`), is exported from `index.ts` and gets a test.

## Tests

Every app and package keeps its tests in `tests/`, mirroring `src` down to the slice: `tests/features/<name>/`,
`tests/shared/lib/`, `tests/app/`, `packages/ui/tests/{components,captcha,map}/`. Pure functions in `model/`
get unit tests; dashboard route guards are tested through a memory router (`tests/app/routes.test.tsx`).
